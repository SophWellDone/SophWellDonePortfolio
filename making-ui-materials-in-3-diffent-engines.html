Blog - Making UI Materials in 3 Different Engines

Sophie Wheldon
March 26, 2026
Updated on March 29, 2026

The goal of this project is to learn how to create UI materials and shaders in 3 different Game engines: Godot, Unreal and Unity. More specifically, the aim is to create an ability cooldown UI system inspired by several hero shooters and similar genres.

Gathering inspiration

I started by gathering inspiration from games that heavily feature distinct abilities. I am also looking at the default layouts without any customisation or accessibilty settings.

Warframe

Warframe has a very unobtrusive display for the current characters abilities. A horizontal progress bar displays the users current energy, with the actual number displayed below. Above the bar is the 4 Warframe-specific abilities, represented with iconography. This system relies on colouring these icons based on the abilities status:

  • Blue signifies an ability is currently active
  • White signifies an ability is ready to be cast 
  • Grey signifies an ability is not ready

A potential issue with this colour coding system is colour blind users may struggle to discern which colour and state the ability is in

However, there are some strengths of this display. The energy bar has a pulsating animation, making the bar feel as if it is made from pure energy itself. This is arguably much more immersive than just having a flat progress bar.

Overwatch

Overwatch takes an opposite approach. Clean, flat and easy to read, Overwatch's UI is more adapted to it's competitive multiplayer hero shooter genre. One thing to note while comparing is that, whilst Warframe uses a shared energy system for most abilities, Overwatch has dedicated cooldowns for each one.  

Whilst the colours are customisable, the general principle remains similar to the icons from Warframe but with enhanced visual changes for different states:

  • When an ability is not ready, the entire panel becomes crossed out and the icon is faded away. 
  • When an ability is on cooldown, the button is greyed out and becomes a (bottom-to-top) vertical progress bar, with the seconds remaining overlayed. 
  • An active ability will have a solid colour overlay.

Destiny 2

Destiny 2 was the final game looked at. It follows a similar approach to Overwatch by making the ability icon/panel a progress bar for time remaining when on cooldown. It also features a progress bar for the cooldown of the Super (A powerful, less frequently available ability) above the smaller cooldowns and weapon information.  

Destiny 2 also opts for a flat UI design, comprised mostly of both opaque and transparent boxes with some icons to show what the user has equipped. It uses colour to display elements and types rather than the ability status itself.  A potential issue is that abilities on cooldown could blend in with the rest of the game world, especially when looking at bright white areas, as they are essentially only a small transparent box with very thin white borders and equally transparent iconography.

The Overwatch timer is both in the 'Potential Flaws' and 'Features I Like' rows as it is arguable whether the timer is necessary. Whilst a split second makes a big difference in a multiplayer FPS game, most skilled players will be focused on aiming and the 3D space around them rather than watching a timer tick down. On the other hand, seeing the exact amount of seconds left could be enough information to decide whether commiting to a certain play is a good idea or not. 

Concepts for Design

Concept 1 - Water 

I used illustrator to rapidly test and plan out my design before getting started in-engine.

The first concept was started flat and focused on being as minimilstic as possible. It follows the Overwatch 2 / Destiny style of filling up the panel and changing colour once done.

I decided to take it in a water-themed direction where the progress bar would slosh around when progressing and would 'overflow' when the ability is ready, dropping water particles and creating a animated border that rotates around the ability.

This is both an aethstetic choice but also aims to grab the users attention, especially when the bar fills.

Selective attention is the process of focusing on a particular object in the environment for a certain period of time. Attention is a limited resource, so selective attention allows us to tune out unimportant details and focus on what matters. Cherry, K. (2023)

 Players who selectively paying attention to the game world - surviving and shooting - don't need to directly focus their vision at the button to see it is so full it is 'bursting' and spilling water droplets at the bottom of the screen.

Concept 2 - Right Angle Design

The second concept is a right angle based design that displays information. A ripple/exploding effect will trigger after it fills completely. 

Putting it In-Engine

Godot

Making the pixel space

Started with the control node setup. This is quite simple in Godot - A HBoxContainer does the heavy lifting for organising, and I have an empty shader material on each of the squares.

I started by trying to make a pixel grid that was also centered to help with checking where the border should be shown.

const vec2 BORDER_WIDTH = vec2(2,2);
const vec2 PANEL_SIZE = vec2(32, 32);


void fragment() {
	//Centre UV
	COLOR.rg = (UV - vec2(0.5,0.5)) * 2.0;
	
	//Snap UV to pixel
	vec2 pixel_snap = vec2(1.0,1.0) / PANEL_SIZE;
	COLOR.rg = vec2(step(COLOR.r, pixel_snap.x), step(COLOR.g, pixel_snap.y));
	
}

This didnt work as the step function returns a boolean rather than what i expected - rounding to the nearest multiple of the integer.

The solution was simple - divide the UV by the inverse of the amount of pixels, then round that value and multiply it back up to reset the range to 0➡️1

	//Snap UV to pixel
	vec2 pixel_snap = vec2(1.0,1.0) / PANEL_SIZE;
	COLOR.rg = round(UV/pixel_snap)*pixel_snap;

Another issue was that the changes to COLOR.rg weren't being stored, so the centering didnt save. To keep the shaders 'pixels' on the actual grid the round() was changed to afloor()

// Diagonal Ability Cooldown Shader by Sophie Wheldon

shader_type canvas_item;

const vec2 BORDER_WIDTH = vec2(2,2); // pixels
const vec2 PANEL_SIZE = vec2(64, 64); //pixels

void fragment() {
	//Centre UV
	vec2 center_uv = (UV - vec2(0.5,0.5)) * 2.0;
	
	//Snap UV to pixel
	vec2 pixel_snap = vec2(2.0,2.0) / PANEL_SIZE;
	COLOR.rg = floor(center_uv/pixel_snap)*pixel_snap; //floor is used so pixels stay on actual integers.
}

Defining a border

My first attempt had a lopsided border that didnt match the pixel grid outside of the shader. After some testing I realised the pixels were also not alligned with the actual pixel grid.

The fix was just in the calculating pixel_uv line. By adding half of an individual pixel, it offset the pixels in UV space by a half, making it line up with the actual screen pixels and properly centering it.

//Snap UV to pixel
	vec2 pixel_snap = vec2(1.0,1.0) / PANEL_SIZE;
	vec2 pixel_uv = floor((UV+pixel_snap/2.0)/pixel_snap)*pixel_snap; //floor is used so pixels stay on actual integers.

Progress Mask

To make this an actual progress bar, the diagonal needs to be added. All i knew going in was that diagonal lines take the form of y = x or x + y = 0. 

// Diagonal Ability Cooldown Shader by Sophie Wheldon

shader_type canvas_item;

const vec2 BORDER_WIDTH = vec2(2,2); // pixels
const vec2 PANEL_SIZE = vec2(64, 64); //pixels

uniform float fill_progress = 1.0;

// Erases diagonal border the lower fill_progress is.
float progress_mask(vec2 uv){
	return abs(uv.x + uv.y - 1.0);
}

// Checks if uv coordinate is near enough to the edge to be in the border.
bool is_border(vec2 uv){
	vec2 min_border_uv = BORDER_WIDTH/PANEL_SIZE;
	return (uv.x >= 1.0-min_border_uv.x) || (uv.y >= 1.0-min_border_uv.y)||(uv.x<min_border_uv.x)||(uv.y<min_border_uv.y);
}

// Snaps UV coordinate to nearest world-space pixel.
vec2 uv_to_pixel_coordinate(vec2 uv){
	vec2 pixel_step = vec2(1.0) / PANEL_SIZE;
	//vec2 pixel_offset = pixel_step * 0.5;
	
	return floor((uv) / pixel_step) * pixel_step;
}


void fragment(){
	vec2 pixel_uv = uv_to_pixel_coordinate((UV));
	
	COLOR = vec4(0.0);
	if (is_border(pixel_uv)){
		COLOR = vec4(1.0 * progress_mask(pixel_uv));
	}
	
}

By reorganising the steps into different functions, it was easier to test new ways of achieving the mask. The current output at this point was a nice gradient mask when fill_progress was 1.0, but the progress would go off center rather than increasing / decreasing.

After a little trial and error, a way to center it and clamp the values between 0 and 1 was found!

uniform float fill_progress = 1.0; //%, as  range from 0 to 1

// Erases diagonal border the lower fill_progress is.
float progress_mask(vec2 uv){
	float fill_check = (1.0-fill_progress) * 2.0;
	return abs(uv.x + uv.y-1.0) + 1.0 - fill_check;
}

By attaching a slider to the fill_progress parameter the shader can be animated

When using thestep() function to make hard edges, the values were not centered yet again and they only became visible from 0.5 onwards.

Overcoming Repeating issues

I decided to try something different. I booted up demsos graphic calculator to specifically test this diagnoal masking function. It didnt take too long to create a new solution. The red/darker area indicates where border pixels will be fully white, whilst the orange space could be used for a smoother gradient edge.

// Diagonal Ability Cooldown Shader by Sophie Wheldon
shader_type canvas_item;

const vec2 BORDER_WIDTH = vec2(2,2); // pixels
const vec2 PANEL_SIZE = vec2(64, 64); //pixels

// Percentage as a range from 0 to 1. display cooldown remaining on this ability.
uniform float fill_progress = 1.0;
 
//Defines the size of the grey boundary. This percent will be added atop the fill_progress
// to create a semi-transparent section of the boundary, even when fill_progress is at 0% 
uniform float edge_smooth = 0.1; 

// Alpha values for the two boundaries above.
uniform float fill_alpha = 1.0;
uniform float fill_smooth = 0.5;



// Erases diagonal border the lower fill_progress is.
float progress_mask(vec2 uv){
	
	// returns 0 to 1 based on how close to the diagonal center this pixel is
	float test_value = abs(uv.x+uv.y-1.0);
	
	// completely in the mask - this percent fill has been reached
	if (test_value > 1.0-fill_progress){
		return fill_alpha; 
		}
	// smooth edge - keeps corners even when  at 0%
	if (test_value > 1.0-fill_progress-edge_smooth){
		return fill_smooth; 
		}
	return 0.0;	
}

// Checks if uv coordinate is near enough to the edge to be in the border.
bool is_border(vec2 uv){
	vec2 min_border_uv = BORDER_WIDTH/PANEL_SIZE;
	return (uv.x >= 1.0-min_border_uv.x) || (uv.y >= 1.0-min_border_uv.y)||(uv.x<min_border_uv.x)||(uv.y<min_border_uv.y);
}

// Snaps UV coordinate to nearest world-space pixel.
vec2 uv_to_pixel_coordinate(vec2 uv){
	vec2 pixel_step = vec2(1.0) / PANEL_SIZE;
	//vec2 pixel_offset = pixel_step * 0.5;
	
	return floor((uv) / pixel_step) * pixel_step;
}


void fragment(){
	vec2 pixel_uv = uv_to_pixel_coordinate((UV));
	
	COLOR = vec4(0.0);
	if (is_border(pixel_uv)){
		COLOR = vec4(1.0 * progress_mask(UV));
	}	
}

The final step was making everything use uniform variables for UI designers to be able to customise the border. To line up with the original plan, colours were added with an optional system for lerping the colour based on fill progress.

group_uniforms colour_settings;

// Alpha values for the two boundaries above, plus the boundary outside of the current progress.
uniform vec4 solid_colour : source_color = vec4(0.278, 0.675, 0.949,1.0);
uniform vec4 smooth_colour : source_color = vec4(0.278, 0.675, 0.949, 0.5);
uniform vec4 empty_colour : source_color = vec4(1.0, 1.0, 1.0, 0.196);

//Optionally lerp colour for progress value too
uniform bool change_colour_with_progress = true;
uniform vec4 solid_low_colour : source_color = vec4(1.0, 0.247, 0.349,1.0);
uniform vec4 smooth_low_colour : source_color = vec4(1.0, 0.247, 0.349,0.5);

// Erases diagonal border the lower fill_progress is. 
// Note: Now returns a vec4 colour rather than a float
vec4 get_progress_colour(vec2 uv){
	
	// returns 0 to 1 based on how close to the diagonal center this pixel is
	float test_value = flip_h ? abs(uv.x+uv.y-1.0) : 1.0 - abs(uv.x+uv.y-1.0);
	
	// completely in the mask - this percent fill has been reached
	if (test_value > 1.0-fill_progress){
		if (change_colour_with_progress){
			return mix(solid_low_colour, solid_colour, fill_progress);
		}
		return solid_colour;
	}

	// smooth edge - keeps corners even when  at 0%
	if (test_value > 1.0-fill_progress-edge_smooth){
		if (change_colour_with_progress){
			return mix(smooth_low_colour, smooth_colour, fill_progress);
			}
		return smooth_colour; 
		}
		
	return empty_colour;
}

Code review

I decided to leave it here as I had already spent many hours (and several minutes-worth of writing on this post) working on the angular shader.

The code evolved a lot and I learned a lot working on it! But to make the process of porting this over more effecient, I can use this knowledge to plan the steps I need to take to remake this:

  • Define the variables - 5 Colours, a border_size, the current progress,
  • Make a border by figuring out big the outer x pixels of the UV space is.
  • Cut out the diagonal by adding the x and v values
  • Create the smooth area by repeating the check above with a lower threshold.
